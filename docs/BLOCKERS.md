# What stands between this and production

An honest list, for the three-round committee path (the one fast enough to deploy). It is the
builder's own list, not an audit; a reviewer will add to it. Status as of 2026-11-25. Also done since the first version: the share partition now uses the paper's tables.

## Would leak or lose a key

| # | Blocker | Status |
|---|---|---|
| 1 | The protocol was written from the paper and never compared with the authors' implementation. A subtle deviation in the rejection step can leak the key over many signatures without any test failing. | **Done as far as code can show.** Compared line by line with the authors' [reference implementation](https://github.com/Threshold-ML-DSA/Threshold-ML-DSA) (`thmldsa65/internal`). Identical: all fifteen (K, r, r') parameter sets and nu = 6, the hyperball sampler, rounding, the rejection test, the sharing tables and their relabelling (now a test), challenge derivation and the combine checks. One difference found and aligned: the reference rejects a hint-error norm equal to gamma2, cairn accepted it. cairn is stricter in two places (commit-then-reveal of openings, a final standard verification). The two also sign together: `scripts/reference-interop.sh` has the reference deal a key, cairn import the shares and rebuild the same public key, and mixed committees (2-of-3 to 4-of-5, cairn in the minority and the majority) run the protocol; both combine procedures return the same bytes on every transcript, and cairn's public response check clears the reference's parties. Repeated at scale on 2026-11-27: 600 reference-dealt keys, 1,206 attempts, same bytes every time, and the same answer rate from both implementations' parties. A statistical test of the published responses (`scripts/leak-check.sh`) found no lean towards the share over 105,000 responses; it would see a missing rejection step, and a partial one only above about 42% of that. A review by the authors is not being sought: their public code answered the questions; what it cannot answer falls under items 2 and 15. |
| 2 | Masks were sampled with `f64` arithmetic and a textbook Gaussian method; the security argument assumes an exact distribution. | Mostly done. The sampler and the rejection test now run in double-double arithmetic (about 106 bits) on 106-bit uniforms, and are checked against a 256-bit evaluation of the same formula: no coordinate rounds differently and the largest error before rounding is about 1e-26 (it was 6e-10 with `f64`). By a counting estimate the masks are within about 2^-73 statistical distance of ideal per mask, against about 2^-18 before. [SAMPLER.md](SAMPLER.md) has the method and its limits: it is an estimate with a stated assumption, not a proof, and whether the paper's proof absorbs it has not been worked through. |
| 3 | Arithmetic and the rejection test are not constant time. | Partly. Modular reduction is division-free and branch-free at the source level. The sampler no longer calls the system `ln` and `cos`: its own are fixed operation sequences, and `scripts/ct-check.sh` reads the compiled code of both and finds no call and no data-dependent branch (arm64 only). A timing measurement of the response round (`scripts/timing-check.sh`) found the processor taking share-dependent time on an Apple M3; signing threads now set the arm64 data-independent-timing bit and the difference is gone ([SAMPLER.md](SAMPLER.md)). Secrets are erased on drop. The mask round was measured the same way and showed no difference. Still open: x86-64, where only the operating system can set the equivalent bit and no measurement has been made; share file handling and key generation, which were not measured; the machine code of everything else; and secret expansion in key generation, which is FIPS 204's own rejection sampler. |
| 4 | A trusted dealer created the key, every share, the TLS authority and every node's TLS key on one machine. | **Mostly done.** `cairn dkg` implements the paper's distributed key generation: no machine holds the whole key, and seeds travel end-to-end encrypted so the coordinator and TLS authority see only ciphertext. Node TLS no longer has an authority: each machine can make its own certificate (`cairn tls-rotate`) and peers pin its fingerprint. Still open: parties must exchange identity public keys and certificate fingerprints out of band, and the implementation is as unreviewed as the rest. |
| 5 | No share refresh, no replacing a party, no certificate rotation or revocation. | Partly. A party that lost its machine can get its share back from the others (`cairn share-recover` / `share-help`): requests are signed with identity keys, secrets travel sealed end to end, and each is checked against the committee's public per-subset keys. That restores availability only. A share that leaked stays valid: there is no refresh, because adding a sharing of zero would break the shortness the scheme's shares need, and the paper gives no alternative. The remedy for a suspected leak is a new key by DKG. TLS certificates can be rotated and revoked on a running committee (`cairn tls-rotate`, `tls-pin`, `tls-unpin`; [OPERATIONS.md](OPERATIONS.md)): trust is a per-machine fingerprint table that is re-read when it changes. |
| 6 | Mask state is memory only. A crash loses it safely, but nothing stops a cloned or snapshot-restored machine from answering twice with one mask, which reveals its share. | Partly. Unused masks and half-finished sessions are erased after 120 s, which bounds what a restored snapshot can replay to that window. The rule still stands: never clone or restore a running party. |

## Would stop an operator deploying it

| # | Blocker | Status |
|---|---|---|
| 7 | The KMS endpoint accepted requests from anyone who could reach it. | **Done.** Requests are verified against AWS SigV4 credentials, tested with the stock pqc-sidecar's own AWS client; without credentials the endpoint binds loopback only. The hop can run over HTTPS (`--tls-cert`, certificate from `cairn kms-cert`); the stock pqc-sidecar trusts it through `SSL_CERT_FILE` and refuses the endpoint without it (`scripts/kms-interop.sh`). |
| 8 | Signing policy was a hard-coded prefix check, and parties trusted the coordinator's choice of message. | **Done for checkpoints.** Each party parses the checkpoint itself and refuses the wrong key, unlisted chains, a lower height, or a second checkpoint at a height, with the last height kept on disk. Other message types are not supported. |
| 9 | A wrong response is detected but cannot be attributed; a persistent bad party is found only by rotation. | **Done.** The committee key keeps the per-subset public keys, so anyone can check one party's response against public values; a wrong response is named and the party excluded. |
| 10 | The coordinator is a single point of failure for availability (not for secrecy). | **Done for a crashed coordinator.** A standby coordinator with its own certificate runs beside the first, and `cairn kms-failover`, a TCP relay that holds no key and runs beside the sidecar, sends each connection to the first coordinator that accepts it. `scripts/failover-check.sh`: an unmodified pqc-sidecar kept getting certificates while the active coordinator was killed, and again when the roles were swapped. The parties refuse a conflicting checkpoint from either coordinator. Not covered: a coordinator that is up but cannot sign still receives connections. |
| 11 | Latency on real links: 3-of-4 took 3.9 s between a home connection and Helsinki, against a 2 to 3 s target. One link measured. | Partly. Masks are precomputed, and the coordinator now runs two executions side by side and keeps the first signature: with 180 ms injected round-trip time, 3-of-4 went from 922 to 712 ms mean and from 2.3 to 1.2 s at the 95th percentile. Injected delay does not model bandwidth, which is what limited the real link, and side-by-side executions send more bytes, not fewer. The real link has not been measured again. |
| 12 | Cost grows steeply with the threshold; practical committees are 2-of-3 to 3-of-5. | Inherent to the scheme's parameters. |
| 13 | No metrics, alerting, backup procedure, upgrade path or packaged release. | **Mostly done.** Coordinator and parties serve Prometheus counters (`--metrics-listen`). `scripts/alerts-check.sh` validates [`deploy/prometheus-alerts.yml`](../deploy/prometheus-alerts.yml) with promtool, unit-tests every alert, and has a real Prometheus scrape a live committee and evaluate the rules (this found and fixed a rule that stayed silent with no party up). `scripts/upgrade-rehearsal.sh` rehearsed a rolling upgrade from the published v0.3.0 binary to v0.4.0: each party, then the coordinator, with a certificate after every step under the same key. Releases are built with checksums by a workflow. [OPERATIONS.md](OPERATIONS.md) has backup, rotation, standby and upgrade procedures. The same script then rehearses an upgrade across a wire-version change (stop the coordinator, replace every party, start it again), from v0.4.0 to the current build. Not done: alerts delivered through an Alertmanager, a migration tool for file formats. |
| 14 | Never run against a real chain; every live run used a CometBFT stand-in. | Partly. `scripts/real-chain-demo.sh`: an unmodified pqc-sidecar followed Cosmos Hub mainnet through a public RPC in light-client mode and a local 3-of-4 committee signed blocks 34,035,530 and 34,035,540. Not done: operators on separate hosts, long-running operation, a chain that consumes the certificates. |

## Only others can provide

| # | Blocker | Status |
|---|---|---|
| 15 | Independent security review. | Open. Not funded. [REVIEW_REQUEST.md](REVIEW_REQUEST.md) asks five scoped questions of any reader. In its place for now: the measurements in DECISIONS.md D-140 (response leak test, differential runs against the reference, coverage-guided fuzzing, advisory check), each with a stated reach. They are not a review. |
| 16 | The signatures verify under FIPS 204, but the signing procedure is not the FIPS 204 algorithm and nothing is FIPS 140 validated. NIST's threshold process is still open. | Open, and outside this project's control. |
| 17 | A written security argument for cairn's own additions (coordinator relay, precomputed masks, fault handling, policy). | Partly. [SECURITY_ARGUMENT.md](SECURITY_ARGUMENT.md) states a claim, an argument and its limits for each addition, and ends with a list of gaps. Its first gap is closed in code: a dishonest coordinator could show different parties different commitment sets, and now each party signs the set it was shown and answers only if every other active party signed the same one (tested). It remains the builder's argument, not a proof and not reviewed. |
