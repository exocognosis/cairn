# cairn

Committee-tower threshold ML-DSA-65 signing for proof-of-stake checkpoints.

A quorum of validators produces **one standard 3,309-byte FIPS 204 ML-DSA-65 signature** over a
finalized checkpoint. It is emitted in PQC Sidecar's existing `.pqcc` certificate format and
verified by unmodified `pqc-sidecar verify`, the `pqc-sidecar-verify` npm package, and any
off-the-shelf FIPS 204 library. No verifier changes, no new cryptography on the verifying side.

## Status: v1, research build

Read this before using anything here.

| | |
|---|---|
| **Works, tested** | The protocol, tower, retry and fault logic; exact FIPS 204 output (byte-identical to a single deterministic signer); `.pqcc` v2 certificates accepted by three independent unmodified verifiers; a KMS-compatible endpoint that a stock pqc-sidecar can sign through. |
| **Not secure computation** | The non-linear half of every signing attempt runs behind an `AttemptEngine` trait. v1 ships one implementation, `TrustedEngine`, an in-process *ideal functionality*: the process running it sees the signing seed and every rejected candidate. It is a stand-in for a real MPC, not one. |
| **One process** | All 16 signers run in one process over an in-memory broadcast channel. There is no network transport, and round timeouts are logical (accounted, not waited). |
| **Trusted dealer** | The key is generated by a dealer and shared down the tower. Dealerless generation is not implemented. |
| **Virtual root parties** | A leaf committee acts as one party of the root committee. Making that real needs each leaf to jointly emulate a root-MPC party; v1 models it with sealed values. This is the main open problem (ARCHITECTURE.md, "What v1 does not solve"). |
| **Unreviewed** | No security proof of the composed protocol, no external review, not constant time. |

So: this repository demonstrates that the architecture produces standard signatures end to end
and pins down every interface. It is not threshold custody yet.

## Why a tower: the N = 6 wall

ML-DSA signing is hostile to MPC. `ExpandMask` is SHAKE256 over a secret seed, `HighBits` and
`LowBits` are non-linear rounding, and Fiat-Shamir with aborts repeats the whole computation
about five times per signature. The predecessor prototype
([lattice-aggregation](https://github.com/exocognosis/lattice-aggregation)) ran the exact FIPS
204 mask inside a malicious-secure dishonest-majority MPC: N = 4 (3-of-4) costs 28 GB of
traffic, N = 5 costs 55 GB, and N = 6 failed on a 16 GiB host. One MPC over a validator set is
not an option.

cairn therefore never runs an interactive committee larger than six (`MAX_COMMITTEE`, enforced
in the type constructors) and reaches more signers by nesting committees:

```
                       root committee, 3-of-4            <- non-linear engine runs here
               /            |            |           \
        leaf 1 (3-of-4) leaf 2 (3-of-4) leaf 3 (3-of-4) leaf 4 (3-of-4)
        s s s s         s s s s         s s s s         s s s s           16 signers
```

The key is Shamir-shared 3-of-4 across the leaves, and each leaf's share 3-of-4 across its
signers. A signer's effective share is its share times the product of the Lagrange coefficients
on its path, so the linear part of signing (`z = y + c·s1`, `r = A·y − c·s2`) is done locally by
each signer and summed. Only the root tier evaluates the non-linear functions, among at most six
parties.

## What the Lean 4 model gives

The corruption bounds of the composition come from the `CertTowers` Lean 4 library (99 theorems,
no `sorry`; private, not vendored here). `cascade-tower` evaluates the closed forms of its
read-once threshold-tree results:

| Property | 3-of-4 × 3-of-4 | Theorem |
|---|---|---|
| Fewest corrupt signers that can sign | 9 of 16 (`∏ t_j`) | `CertTowers.Access.minAuth_isLeast` |
| Fewest offline signers that can block | 4 of 16 (`∏ (k_j − t_j + 1)`) | `CertTowers.Access.minBlock_isLeast` |
| Pr[root compromised], i.i.d. corruption 10% | ≈ 2 × 10⁻⁷ (binomial tail, iterated) | `CertTowers.ThresholdTree.rootProb_list` |

A unit test checks the first two against brute force over all 65,536 signer subsets. Note what
the bounds are: nine corrupt signers suffice only in the worst placement (three in each of three
leaves); a flat 9-of-16 threshold would need nine in any placement. The tower trades that margin
for committees small enough to run. The deterministic stake-weighted epoch assignment spreads
stake across leaves, and `Assignment::exposure` evaluates the access function for any given
corrupt set.

## Quickstart

Requires Rust 1.80+. The external-verifier checks also need Node 20+ and a pqc-sidecar checkout
next to this repository.

```bash
cargo test --workspace
```

```bash
./scripts/setup-verifiers.sh
```

```bash
CAIRN_REQUIRE_EXTERNAL_VERIFIERS=1 cargo test -p cairn-sidecar --test e2e -- --nocapture
```

`setup-verifiers.sh` builds the pqc-sidecar checkout as is (into `target/`, nothing is written
to the checkout) and installs the published `@exocognosis/pqc-sidecar-verify`. Without it, the
end-to-end test still verifies with RustCrypto `ml-dsa` and prints a `SKIPPED` line for each
missing external verifier.

Produce and check a certificate by hand:

```bash
cargo run --release -p cairn-sidecar -- demo --out out
```

```bash
target/pqc-sidecar/release/pqc-sidecar verify --certificate out/00000000000000001200.pqcc --public-key out/public_key.hex
```

### Signing through an unmodified pqc-sidecar

pqc-sidecar's `aws_kms` signer backend has an endpoint override. `cairn serve-kms` answers the
two KMS calls that backend makes, so a stock sidecar keeps watching the chain, checking finality
and writing certificates while the tower signs:

```bash
cargo run --release -p cairn-sidecar -- serve-kms --listen 127.0.0.1:8200 --public-key-out public_key.hex
```

```toml
[signer]
backend = "aws_kms"
aws_kms_key_id = "alias/cairn-tower"
aws_region = "us-east-1"
aws_endpoint_url = "http://127.0.0.1:8200"
public_key_file = "public_key.hex"

[checkpoint]
interval = 100   # checkpoint cadence: every K finalized blocks
```

`./scripts/kms-interop.sh` runs the unmodified sidecar binary's own KMS client against the
endpoint. The endpoint does not authenticate requests; bind it to loopback.

## Benchmarks

```bash
cargo run --release -p cairn-sidecar -- bench --signatures 500 --json target/bench.json
```

16 signers (3-of-4 × 3-of-4), 500 certificates per scenario, Apple M3, single process:

| scenario | latency ms (mean / p50 / p95 / max) | rejected attempts (mean / p95 / max) | fault retries | timeout wait ms | signer bytes (mean / max) | relay bytes (mean) | messages |
|---|---|---|---|---|---|---|---|
| healthy | 33.1 / 25.7 / 90.3 / 210.4 | 4.07 / 13 / 32 | 0.00 | 0 | 7,057 / 17,446 | 26,162 | 264 |
| one signer offline | 34.3 / 26.3 / 91.9 / 183.0 | 4.19 / 13 / 27 | 0.00 | 2,000 | 7,101 / 15,586 | 26,228 | 270 |
| one signer malicious | 37.2 / 32.0 / 85.4 / 160.1 | 3.68 / 11 / 22 | 1.00 | 0 | 6,498 / 14,033 | 26,453 | 284 |

How to read this:

- **Latency is in-process compute only.** It excludes network delay and the cost of a real MPC
  for the engine's two phases, which dominates any deployment. The predecessor measured a full
  ML-DSA attempt in MPC in gigabytes of traffic, and a signature needs about five attempts.
  That cost, not the numbers below, sets real latency, which is why the target is checkpoint
  cadence and not per-block signing.
- **Rejected attempts** follow the ML-DSA-65 abort distribution (mean ≈ 4.1 rejected, so ≈ 5.1
  attempts per signature). The tower does not change it: the mask is the FIPS 204 one.
- **Signer bytes** are what one participating signer broadcasts per certificate, summed over all
  attempts (≈ 7 kB; 5.2 kB of it is the single `z` opening of the accepted attempt). **Relay
  bytes** are what a committee's coordinator rebroadcasts to the tier above. Neither includes MPC
  traffic.
- **Faults** are injected at every checkpoint (signers are reinstated before each signature), so
  these are worst cases. An offline signer costs one round timeout (2 s here, logical) and no
  retry. A malicious signer is named and excluded, costing one retry.

## Hard invariants

- Signatures are FIPS 204 ML-DSA-65: `ExpandMask` is the exact SHAKE256 expansion (never random
  nonce sampling), encodings are standard (pk 1,952 bytes, signature 3,309 bytes), and no
  verifier is modified. Tests compare every threshold signature byte-for-byte with a single-key
  deterministic signer and with RustCrypto `ml-dsa`.
- Every interactive committee has N ≤ 6.
- A rejected attempt opens `c~` and one bit. No `z` share, hint, or failing bound is revealed,
  and signers erase the attempt's state.
- Certificates are issued only at checkpoint heights (every K finalized blocks).
